Basecamp deep-link test page

Open this file in a browser with Basecamp installed. Each link is the same thing a real page would do — nothing here is faked with JavaScript.

This page cannot tell you whether anything worked. There is no channel back from Basecamp to the browser — deliberately, so a page cannot discover what you have installed. Every verdict below comes from watching the Basecamp window and its log. Keep the log tailing in a terminal while you click.

Before you start

  1. Launch Basecamp once from Finder so LaunchServices registers the scheme.
  2. Tail the log (the installed build is portable, so no Dev suffix): 
    tail -f ~/Library/Application\ Support/Logos/LogosBasecamp/logs/*.log | grep -i link
  3. Note which apps you actually have installed. basecamp://app/<name> only brings forward something that is installed — and by design it reports success either way, so a wrong name looks exactly like a right one from here.

1 · Warm start — Basecamp already running

ClickExpected
basecamp:// Window comes forward. Nothing else. No intent is submitted, so the log stays quiet.
basecamp://app/package_manager_ui Package Manager comes forward, with no dialog. Routed to a section switch, not the app launcher — the Package Manager is hoisted into the section stack rather than docked, so the launcher has nothing to raise. Same mechanism as the Welcome page’s “manage packages” button. Log: dispatching link request … for intent basecamp.apps.launch
basecamp://intent/basecamp.settings.open Switches to Settings, no dialog. The shell is the only provider, so the chooser is skipped.
basecamp://intent/basecamp.apps.open Switches to the App Manager.
basecamp://intent/basecamp.packages.open Switches to the Package Manager. Use this rather than basecamp://app/package_manager_ui: the Package Manager is shell chrome hoisted into the section stack. Both links now reach it — this one says so explicitly, and basecamp://app/package_manager_ui is redirected to the same section switch.
basecamp://intent/basecamp.repositories.manage Settings, on the Repositories page — one level deeper than settings.open. This is the intent the Package Manager raises from its own “Manage Repositories” button.

1b · Real apps from the Logos catalog

Install these from the Package Manager first — they are ordinary catalog apps, not fixtures. Names verified against logos-modules-release’s index.json.

Install before clicking, or you prove nothing. basecamp.apps.launch answers ok whether or not the app exists — deliberately, so a web page cannot discover what you have installed by trying names. A link to a missing app is indistinguishable from a link to an installed one, from the browser. The difference is only visible in Basecamp.
ClickExpected once installed
basecamp://app/blockchain_ui Blockchain comes forward. Pulls in blockchain_module as a dependency, so give the first launch a moment.
basecamp://app/chat_ui Chat comes forward (needs chat_module, delivery_module).
basecamp://app/storage_ui Storage comes forward.
basecamp://app/lez_wallet_ui LEZ Wallet comes forward.
basecamp://app/amm_ui Logos DEX App comes forward.
basecamp://app/definitely_not_installed Control. Nothing visible happens — and note it looks exactly like a success from here. If Basecamp offers to install something, that is the catalog suggestion, which is between the shell and you and is never reported back to the page.

The log line is the real verdict for every row above:
LinkRequestCoordinator: dispatching link request … for intent basecamp.apps.launch

2 · Cold start — quit Basecamp first

Quit fully (⌘Q, or osascript -e 'quit app "LogosBasecamp"'), then click. The OS launches the app from the registered command. Expect several seconds of nothing — the URL is parked until the intent registry finishes its first build. That delay is the design, not a hang: acting sooner would answer every cold-start link “unavailable”.
Click (with Basecamp quit)Expected
basecamp://app/package_manager_ui Basecamp starts, finishes scanning, then Package Manager comes forward on its own.
basecamp://intent/basecamp.settings.open Basecamp starts and lands on Settings.
basecamp://app/blockchain_ui The interesting cold case: Basecamp starts, scans, loads blockchain_module, then Blockchain appears. Longest wait of any link here, and the one most likely to look broken while it is simply working.

3 · Things that must not work

The negative cases matter as much as the positive ones: a build where every link worked would pass section 1 just as happily.

ClickExpected
…confirm_uninstall Nothing happens. No dialog, nothing removed. Not in the shell’s web-reachable set, so the link requester never declared it — refused at the broker’s first gate, before any provider is consulted.
…confirm_install Also nothing. Installing is not reachable from a web page either.
basecamp://intent/Wallet.Send Rejected by the name grammar (uppercase). Log: fails the intent-name grammar
basecamp://launch/… Unknown form — only app and intent are accepted.
…?p=!!!notbase64 Rejected before anything is submitted. Log: not valid base64url
…?params=e30 Unknown query key. Refused rather than ignored, so a typo is visible instead of surfacing later as an empty payload.

4 · A typed payload

p is base64url of a JSON object. Types survive the round trip, which is why it is not query pairs — the broker type-checks against the provider’s declared params, and ?amount=12.5 would arrive as the string “12.5”.

ClickExpected
wallet.send with {to:"0xabc", amount:12.5} With no wallet installed: nothing visible, and the log shows the request was refused for want of a provider. With one installed that opted in via "web": true: the chooser appears. An installed wallet that did not opt in must never be offered.

What “it works” looks like

LinkRequestCoordinator: dispatching link request link-1 for intent basecamp.settings.open

That line is the only proof the running instance acted. On a warm click the second process forwards and exits silently — “forwarded” and “received” are indistinguishable from outside without it.
